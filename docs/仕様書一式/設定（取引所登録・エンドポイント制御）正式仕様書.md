設定（取引所登録・エンドポイント制御）
1. 本章の位置づけとゴール

本章は、NEXT プロジェクトにおける Collector Phase1 のうち、
以下の責務を 仕様として固定することを目的とする。

取引所の登録方法

実際に使用する API エンドポイントの確定

エンドポイントの on/off・優先度・収集周期の制御方法

UI 保存・設定反映・Collector 実行の責務分離

設定の正準（どのファイルが最終決定か）

Phase1 ゴール定義

Collector が「事実値に基づいた設定」で現物取引所を回せる状態

本章は Phase1（24時間安定稼働）を前提とした最小かつ正確な設定仕様のみを扱う。

2. 設計原則（重要）
2.1 設定の正準ルール

NEXT では、設定の正準を以下の優先順位で扱う。

実行時キャンバス（作業中のみ）

人間がアップロードした設定ファイル

NEXT パッケージ内の初期設定（schema / defaults）

実運用時における正準は アップロードされた設定ファイルであり、
キャンバスは常に一時的な作業領域とする。

2.2 schema 契約と未知キーの扱い

UI 保存・設定反映は settings_svc を正準とする

settings_svc は schema に定義されていないキーを保持しない

schema に存在しない設定は 保存時に破棄される

👉
これは事故防止のための 明示的な設計であり、
「設定したつもり」「UI では見えるが実行に効かない」状態を排除する。

3. 取引所登録仕様
3.1 Phase1 で有効な取引所

Phase1 では bitFlyer のみを対象とする。

enabled_exchanges:
  - bitflyer


理由：

現物（BTC_JPY）は解釈がブレにくい

API の動きが安定しておりテスト向き

保存パス・rate/no_data 検証が最短で固まる

3.2 bitFlyer の公式レート上限（事実値）

1 IP あたり 5 分間に 500 リクエスト

換算：
500 / 300 = 1.6667 rps

この値は 事実値として固定し、
安全係数は Phase2 以降で別途扱う。

4. エンドポイント定義（endpoints.yaml）
4.1 endpoints.yaml の役割

URL / method / API の事実定義

エンドポイントの「存在」を定義する層

収集の有効・無効や周期は ここでは決めない

4.2 正準フォーマット（map 形式）

Phase1 での正準形式は map 形式のみとする。

bitflyer:
  orderbook:
    topic: orderbook
    url: https://api.bitflyer.com/v1/board
    method: GET
    max_rps: 1.6667
    burst: 2
    priority: 0

  trades:
    topic: trades
    url: https://api.bitflyer.com/v1/executions
    method: GET
    max_rps: 1.6667
    burst: 2
    priority: 1

禁止事項

items: 形式の使用は禁止
（schema 契約違反となり、settings_svc により破棄される）

5. エンドポイント制御仕様（collector.yaml）
5.1 feeds の役割（最重要）

collector.yaml: feeds は エンドポイント制御の最終決定レイヤである。

on / off

priority（スケジューラ内優先度）

target_interval（収集周期）

👉
endpoints.yaml は定義層、feeds は制御層
この責務分離は Phase1 で確定する。

5.2 Phase1 実効設定（正準）
feeds:
  bitflyer:
    orderbook: { enabled: true, priority: 0, target_interval: 1.0 }
    trades:    { enabled: true, priority: 1, target_interval: 2.0 }


orderbook：1 秒周期

trades：2 秒周期

bitFlyer 公式上限（1.6667 rps）を超えない安全側設定

6. Collector における設定反映フロー（技術仕様）
6.1 設定読み取りの正準経路

Collector は 必ず以下を使用する。

from btcts.settings import svc as settings_svc

settings_svc.load_effective("exchanges")
settings_svc.load_effective("endpoints")
settings_svc.load_effective("collector")
settings_svc.load_effective("rate_control")

禁止

load_yaml() の直接使用（Phase1 以降は禁止）

6.2 build_scheduler の動作仕様

endpoints.yaml（map）を items に正規化

各 endpoint について feeds を検索

feeds が存在すれば以下を 上書きする

enabled

priority

target_interval

Scheduler に登録

検証済みの実効結果例：

('bitflyer', 'orderbook', priority=0, target_interval=1.0)
('bitflyer', 'trades',   priority=1, target_interval=2.0)

7. Phase1 における停止・制御ポリシー
7.1 endpoint 停止方法

Phase1 では enabled: false のみを停止表現として使用する。

orderbook:
  enabled: false


priority=0 等による暗黙停止は禁止

判断ロジックを増やさない

A. 設定レイヤの責務と優先順位（確定）

Phase1 における設定は、以下の 3 レイヤで構成される。

レイヤ	主ファイル	役割	優先度
制御レイヤ	collector.yaml (feeds)	実行時の最終制御（有効/無効・優先度・周期）	最優先
定義レイヤ	endpoints.yaml	API URL / method / topic の事実定義	中
制限レイヤ	exchanges.yaml	取引所単位の公式レート上限（事実値）	下
優先順位ルール（仕様として固定）
feeds (collector.yaml)
  ＞ endpoints.yaml
      ＞ exchanges.yaml


feeds が存在する場合、必ず feeds が最終決定となる

endpoints.yaml / exchanges.yaml の値は、feeds が未指定の場合の補助値としてのみ使われる

B. collector.yaml（feeds）の正式位置づけ
B.1 feeds は「制御の最終決定レイヤ」である

collector.yaml: feeds は以下を唯一決定する。

エンドポイントの有効 / 無効

Scheduler 内の priority

実際の収集周期（target_interval）

例（Phase1 正準）：

feeds:
  bitflyer:
    orderbook: { enabled: true, priority: 0, target_interval: 1.0 }
    trades:    { enabled: true, priority: 1, target_interval: 2.0 }


この設定は、

endpoints.yaml に定義された endpoint を 必ず上書き

exchanges.yaml の公式上限より厳しい制御も許容

する。

C. endpoints.yaml の仕様的制約（重要）
C.1 正準フォーマットは map 形式のみ

Phase1 において、endpoints.yaml は map 形式のみを正規とする。

bitflyer:
  orderbook:
    topic: orderbook
    url: ...
  trades:
    topic: trades
    url: ...

禁止事項

items: 形式は Phase1 では仕様違反

schema 契約に反するため、UI 保存時に破棄される

C.2 endpoints.yaml の max_rps の扱い

endpoints.yaml に存在する max_rps は 補助値

feeds が指定されている場合、実行時には使用されない

→ Phase1 では feeds の target_interval が唯一の実効値となる。

D. exchanges.yaml（exchanges_def）の正式役割
D.1 公式上限の事実値を保持するのみ

exchanges.yaml（および schema）は、

取引所ごとの 公式 API 上限（事実値）

IP 単位の制限

のみを保持する。

例（bitFlyer）：

rate:
  max_rps: 1.6667   # 500 requests / 5 minutes

D.2 Collector の安全設計

Collector は exchanges.rate.max_rps を 直接の周期決定には使用しない

RatePolicy による 安全側抑制・429 回避のために使用する

E. 設定 I/O の正準経路（再確認）

Phase1 以降、Collector は以下の経路のみを使用する。

settings_svc.load_effective("exchanges")
settings_svc.load_effective("endpoints")
settings_svc.load_effective("collector")
settings_svc.load_effective("rate_control")

禁止

load_yaml() の直接使用

schema を経由しない設定読み取り

F. 安全設計上の明示事項（再発防止）

schema に存在しないキーは 保持されない

feeds が存在するのに Collector が参照しない状態は 仕様違反

exchanges の公式値と乖離した設定は 429 リスクとして即是正対象

これらは Phase1 において すべて解消済みであり、
本補足仕様をもって 再発防止のために明文化する。
