## 作業手順の原則（最重要）

### 1. 現物コード主義

* **既存ファイルの修正は、必ずそのファイルの現物コードを確認してから行う**
* 推測・補完・類推による修正は禁止
* コード未提示の状態での「修正案提示」「差分生成」は原則行わない

### 2. 1ファイル1キャンバス運用

* 修正対象ファイルは **1つのキャンバスを人間と GPT が共有** して作業する
* 同一ファイルに対して複数キャンバスを作成しない（混乱防止）
* 既にキャンバスが存在するファイルは **必ずそれを再利用する**

### 3. 差し替え指示の原則

* 修正は必ず以下のいずれかを明示する

  * 全文差し替え
  * 部分差し替え
* 部分差し替えの場合は、**開始位置・終了位置を文章で特定**する

## 新規ファイル作成時の必須ヘッダ

新規ファイルを作成する場合、**必ず以下2行を先頭に記載する**。

```
# path: <repo_root からのフルパス>
# desc: <このファイルの役割を一文で>
```

* `path` は必ず repo_root 起点の相対パス
* `desc` は「誰が・何のために・どこから呼ばれるか」が分かる一文にする
* README / 仕様書などのドキュメントファイルには不要（**コード専用ルール**）

## V1（旧プロジェクト）仕様の扱いについて

### 基本方針

* **V1 の仕様書・資料はすべて「参考資料」扱い**
* Git 管理下には置かない
* NEXT 開発にそのまま復活させない

### 許可される行為

* 設計思想・事故回避思想・制約条件の抽出
* 抽象化したうえで NEXT 用に再定義

### 禁止事項

* V1 のコード・構造・命名をそのままコピーすること
* 「V1 ではこうだった」を理由に NEXT の設計を歪めること

## Collector に関する前提認識（重要）

### 運用前提

* **MAIN 機単体で Collector は起動・停止・収集が完結できなければならない**
* Collector 専用機は *常時稼働用* の補助的存在であり、代替ではない
* UI からの Start / Stop は **常にローカル Collector を制御する**

### 設計思想

* 最優先事項は **API レート制御と事故防止**
* 多重起動・二重収集・孤児プロセスは最悪の事故
* 情報量よりも「止まらず・制限を食らわない」ことを優先

---

## Health / Audit の位置づけ

* Health は **Collector / データ / 設定の結果を観測する層**
* Health から Collector を直接制御しない
* Audit は **事後解析および GPT 共有を前提とした一次ログ**
