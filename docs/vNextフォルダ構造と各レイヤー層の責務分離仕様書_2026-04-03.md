# vNextフォルダ構造と各レイヤー層の責務分離仕様書

更新日: 2026-04-03
位置づけ: 最上位構造仕様 / 長期不変の開発基準
対象: `btcts_next/src/btcts/`

---

## 1. 本仕様書の目的
本仕様書は、BTC Trade System vNext における

- フォルダ構造の正規形
- 各レイヤーの責務境界
- 依存方向の原則
- 実装時の判断基準
- 禁止事項

を固定するための、最上位仕様書である。

今後の実装・改修・整理・レビュー・次GPTへの引継ぎは、原則として本仕様書を基準に判断する。

この仕様書は単なる整理メモではない。
今後の開発で責務を混ぜないための「設計憲法」として扱う。

---

## 2. 背景と問題意識
従来構造では、特に以下の混在が発生していた。

- collector 側に L2 と L3 の責務が混在
- market_engine 側に domain semantics と execution orchestration が混在
- consumer 側に本来 processing 側で持つべき意味解釈が入り込みやすい構造
- 将来の複数 consumer で再利用できる加工が、個別実装として重複しやすい構造

この状態では、以下の問題が起きる。

1. Collector 専用機へ物理分離したい時に、意味解釈まで抱えてしまう
2. replay / runtime / UI で似た処理が重複する
3. 「どこに置くべきか」の判断が毎回揺れる
4. 将来拡張時に責務の借金が増える
5. GPTごとの判断で配置がブレ、次回以降の再開性が下がる

そのため、vNext では

- ingestion は事実と構造
- processing は共通意味と共通加工
- consumers は利用
- orchestration は実行制御
- platform は共通基盤

へと責務を明確化する。

---

## 3. 最上位思想

### 3.1 基本思想
システムは、次の順で情報を価値化する。

1. 取得する
2. 正規化する
3. 再利用可能な特徴量を作る
4. 市場意味へ解釈する
5. consumer向けに整形する
6. 表示・再生・学習・実行に使う

この流れを壊さないことが、構造の第一原則である。

### 3.2 重要原則
- 取得と意味解釈を混ぜない
- 中立特徴量と閾値付き解釈を混ぜない
- 共通加工と consumer 専用整形を混ぜない
- 実行制御と domain logic を混ぜない
- その場しのぎの convenience import で責務境界を壊さない

### 3.3 依存方向原則
依存方向は原則として次の一方向に保つ。

```text
ingestion -> processing/features -> processing/l3_market_semantics -> processing/l4_consumer_models -> consumers
                                     ↑
                           market_engine/execution は L3 を利用する
```

補足:
- `market_engine/execution` は domain owner ではなく、processing の L3 を利用する execution layer とする
- `market_engine/profiles` は execution と L3 を仲介する policy/contract 層とする

## 6. 各レイヤー詳細仕様

# 6.1 ingestion

## 6.1.1 役割
ingestion は「市場事実を壊さず取得し、構造的に下流へ渡せる形へ整える」層である。

### ingestion が扱うもの
- 取得
- 接続
- retry
- resync
- canonical 化
- sequence / gap / continuity の構造的管理
- snapshot / diff の構造的再構築

### ingestion が扱わないもの
- buy pressure / sell pressure の意味判断
- wall の意味解釈
- absorption / sweep の市場意味
- UI向け要約
- 監視向け alert wording
- consumer 固有の read model

---

## 6.1.2 L1 Capture

### 役割
- API / WS provider
- venue adapter
- raw event capture
- rate control
- retry / reconnect / session continuity
- acquisition health

### 置くべきものの例
- provider client
- websocket lane
- raw writer
- session state
- capture watchdog support

### 置いてはいけないもの
- market meaning
- threshold event
- semantic label
- UI summary
- strategy hint

### 判断基準
その処理が「取得し続けるために必要」なら L1。
その処理が「市場の意味を読み取る」なら L1 ではない。

---

## 6.1.3 L2 Canonical

### 役割
- raw -> canonical transform
- event id / packaging
- canonical record contract
- orderbook structural reconstruction
- tradeflow structural aggregation
- sequence / gap / resync structural support

### 置くべきものの例
- `ingestion/event_types.py`
- `ingestion/l2_canonical/orderbook/book_state.py`
- `ingestion/l2_canonical/orderbook/book_apply.py`
- `ingestion/l2_canonical/orderbook/book_rebuilder.py`
- `ingestion/l2_canonical/tradeflow/trade_aggregator.py`

### 置いてはいけないもの
- pressure 判定
- wall_strengthened などの意味イベント
- aggressive_buy / aggressive_sell
- market regime
- structural-use posture decision

### 判断基準
その処理が「事実を再構成するだけ」なら L2。
その処理が「この状態はこういう意味だ」と言い始めたら L2 ではない。

---

# 6.2 processing

processing は「共通の意味」と「共通の加工」を持つ層である。
consumer や collector の convenience ではなく、システム全体で共有すべき真実を持つ。

---

## 6.2.1 features

### 役割
features は「中立で再利用可能な計算結果」を持つ。
ここではまだ市場意味を定義しない。

### 置くべきものの例
- imbalance
- depth summary
- wall ratio
- trade count
- buy volume / sell volume
- trade delta
- avg price

### 置いてはいけないもの
- buy_pressure / sell_pressure
- aggressive_buy / aggressive_sell
- sweep_candidate
- wall_detected
- trust/broken/provisional などの意味状態

### 判断基準
その出力が「どの consumer にも再利用できる中立量」なら features。
その出力が「意味付きラベル」なら features ではない。

### 重要原則
features は threshold をまたぐ意味判定を持たない。
閾値を越えた瞬間に「イベント」や「意味」になったら、それは L3 の責務である。

---

## 6.2.2 L3 Market Semantics

### 役割
L3 は「市場意味の唯一の正本層」である。

ここで初めて、
- pressure
- wall
- pull
- absorption
- sweep
- continuity
- trust
- structural-use interpretation
- tradeflow semantic events

などの意味が定義される。

### 置くべきものの例
- `processing/l3_market_semantics/orderbook/`
- `processing/l3_market_semantics/tradeflow/`
- `processing/l3_market_semantics/microstructure/`
- `processing/l3_market_semantics/continuity/`
- `processing/l3_market_semantics/continuity/models/`
- `processing/l3_market_semantics/zone/`

### L3 のサブ領域

#### orderbook
- liquidity pressure
- wall semantics
- liquidity pull
- enrichment events
- signal state

#### tradeflow
- trade surge
- aggressive buy / sell
- tradeflow meaning events

#### microstructure
- absorption detector
- sweep detector

#### continuity
- series segmentation
- boundary semantics
- trust semantics
- structural-use interpretation
- continuity-aware orderbook assembly
- assembled truth model

#### zone
- near/far zone shaping
- density metadata shaping

### 置いてはいけないもの
- UI wording
- Streamlit component data shape
- replay page 専用表示データ
- monitoring notification wording
- execution scheduler logic

### 判断基準
その処理が「市場状態に意味を与える」なら L3。
その処理が「誰向けにどう見せるか」を決めるなら L3 ではない。

### 最重要原則
L3 は consumer を知らない。
L3 は「UI のための意味」や「replay のための意味」ではなく、システム全体で共有される市場意味の owner である。

---

## 6.2.3 L4 Consumer Models

### 役割
L4 は、L3 の意味を使って consumer 向けに再利用しやすいモデルへ整形する。

ただしここで重要なのは、L4 は

- consumer 専用変換の置き場
nではなく、
- 共有できる加工は shared に寄せる

という shared-first 原則で設計することである。

### L4 の内部構造

```text
processing/l4_consumer_models/
  shared/
  operator_ui/
  monitoring/
  replay/
  ai_training/
  auto_trading/
```

### shared の役割
複数 consumer が使う加工済みデータを集約する。

例:
- common market summary
- liquidity snapshot bundle
- alert candidate bundle
- timeline-ready event bundle
- health/monitoring reusable digest

### per-consumer の役割
最後の薄い適応だけを持つ。

例:
- UI panel 向け shape
- replay view 向け shape
- monitoring 通知 payload
- AI feature bundle shape
- execution signal bundle shape

### 置いてはいけないもの
- 新しい市場意味
- L3 と競合する truth owner
- raw/canonical reconstruction
- ドメインの一次判断

### 判断基準
複数 consumer で共有できる加工なら `shared/`。
最後の用途固有差分だけが per-consumer。

### 最重要原則
L4 は「第二の L3」になってはならない。
L4 は truth を定義しない。truth を再利用可能な形に整えるだけである。

---

# 6.3 consumers

## 6.3.1 役割
consumers は、加工済みの情報を実際に使う層である。

例:
- operator UI
- replay
- monitoring
- AI training
- auto trading

### 置くべきもの
- page / view / presenter
- consumer専用 bridge
- consumer entrypoint
- display / export / interaction

### 置いてはいけないもの
- 新しい市場意味解釈
- raw/canonical rebuild
- trust owner
- common shared summary logic

### 判断基準
そのロジックが「この consumer で使うためのもの」なら consumers。
そのロジックが「他でも再利用できる」なら consumers の外に出す。

---

# 6.4 orchestration

## 6.4.1 役割
orchestration は「どう動かすか」を担当する。
「何を意味するか」は担当しない。

### 置くべきもの
- runtime
- daemon
- runner
- scheduler
- watchdog
- process lifecycle

### 置いてはいけないもの
- pressure 判定
- trust 判定
- market summary
- consumer presentation model

### 判断基準
そのロジックが「処理順序や起動制御」なら orchestration。
そのロジックが「市場意味」なら orchestration ではない。

---

# 6.5 platform

## 6.5.1 役割
platform は共通基盤のみを持つ。

### 置くべきもの
- env
- io
- paths
- settings
- audit
- schema / config support

### 置いてはいけないもの
- market domain logic
- consumer convenience logic
- replay meaning logic
- collector固有判断ロジック

### 判断基準
その処理が「どの domain でも使える基盤」なら platform。
そうでなければ platform に置かない。

## 7. market_engine の位置づけ

### 7.1 market_engine は何か
`market_engine` は processing の L3 owner そのものではない。
市場意味を利用して runtime / replay / onboarding / projection を動かすための実行系・適用系の文脈である。

### 7.2 market_engine の正規責務

#### execution
- realtime execution
- replay execution
- execution façade

#### profiles
- exchange/venueごとの差分 policy
- apply_anchor / apply_diff / validation policy
- zone policy

#### onboarding
- profile draft
- rebuild review
- review policy
- continuity probe
- onboarding runner

#### market_state
- projector
- schema
- writer

### 7.3 やってはいけないこと
- L3 owner に戻ること
- assembler 的な巨大 mixed package を再作成すること
- continuity/trust semantics の本体を再び market_engine 内に抱え込むこと

## 9. 依存ルール

### 9.1 正しい依存方向
- ingestion は processing を import しない
- features は ingestion を使ってよい
- L3 は ingestion / features を使ってよい
- L4 は L3 を使ってよい
- consumers は L4 / L3 を使ってよい
- execution は L3 と profiles を使ってよい

### 9.2 禁止依存
- collector が L3 semantic owner に戻る
- consumers が ingestion を直接使って意味解釈する
- L4 が L3 を差し置いて truth owner になる
- platform が domain logic を持つ
- execution が consumer presentation logic を持つ

## 10. L2 と L3 の境界判断チェックリスト
実装時に迷ったら、以下で判断する。

### L2 に置くべき質問
- これは事実を再構成するだけか
- これは sequence / gap / resync のためか
- これは snapshot / diff の構造的整合のためか
- これは意味ラベルを持たないか

すべて yes なら L2 寄り。

### L3 に置くべき質問
- これは pressure / wall / absorption などの意味を持つか
- これは threshold や policy による interpretation か
- これは trust / continuity / boundary の意味付けか
- これは「こう読める」という判断か

1つでも yes なら L3 の可能性が高い。

## 11. よくあるアンチパターン

### アンチパターン1
collector convenience の中に semantic helper を置く

なぜダメか:
- collector 専用機分離を妨げる
- replay / runtime / UI で hidden dependency になる

### アンチパターン2
features に threshold event を入れる

なぜダメか:
- 中立特徴量と意味判定が混ざる
- 再利用性が落ちる

### アンチパターン3
UI で market meaning を直接組み立てる

なぜダメか:
- consumer ごとに意味がズレる
- 将来の shared 化が困難になる

### アンチパターン4
execution layer に domain owner を戻す

なぜダメか:
- runtime 実装と市場意味が再結合する
- テスト/切り離し/移植が難しくなる

### アンチパターン5
L4 shared を第二の L3 にする

なぜダメか:
- truth owner が二重化する
- どこを直すべきか分からなくなる

## 12. 実装時の判断ルール

### ルール1
まず「この処理は事実か、意味か、整形か、利用か」を言語化する。

### ルール2
再利用できるなら上位 consumer へ寄せず、processing 側に寄せる。

### ルール3
shared にできるものを先に shared 化し、最後だけ consumer 専用にする。

### ルール4
runtime の都合で domain ownership を決めない。

### ルール5
迷ったら、将来 collector 専用機に切り離せるかで考える。
切り離せないなら collector 側に置かない。

### ルール6
迷ったら、複数 consumer で再利用できるかで考える。
再利用できるなら consumer 側に閉じない。

## 13. 将来拡張との整合
この構造は、今の UI や replay だけのためではない。
将来の

- monitoring
- AI training
- auto trading
- 追加 exchange
- 複数 execution runtime

に耐えるための構造である。

特に重要なのは、L4 shared-first 原則である。
同じ内容の加工済みデータを複数 consumer が使うなら、shared に寄せる。
これにより

- 重複計算を減らす
- 一貫性を保つ
- 保守負荷を減らす
- リソース消費を抑える

ことができる。
